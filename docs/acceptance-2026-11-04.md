### 三条未完全满足与两条冲突

1. **T3.4 默认重试受源预算限制。** `shared/config.py` 默认单次8s、额外重试3次、间隔5s，而总源预算45s。完整四次8s加三次5s是47s；最后一次可能被截短，已有耗时也可能使后续等待被拒绝。测试将间隔置零，不能证明默认条件始终完成三次完整重试。见 `shared/http.py:35`、`:41`、`:80`。
2. **T3.5 长限流等待被拒绝。** 等待 reset 有实现，但默认 `max_rate_wait=10s` 且受源预算限制。长 reset 直接降级；这有运行时保护价值，但不是原文不带该限制的“等到 reset 后重试”。见 `shared/http.py:59`、`tests/test_github.py` 的3600秒场景。
3. **T9.2 健康检查未覆盖所有连接与权限。** GitHub/群/Task v2 有真实读取检查，SMTP有登录与NOOP；机器人只检查URL配置。它不能证明机器人连接、权限与送达。见 `shared/health.py`。
4. **T6.4 / T10.3 文案冲突。** task 要求“今日无记录”，proposal 要求“当日无记录”。当前遵循 proposal，输出“当日无记录”；不能同时宣称逐字满足两者。

另外 proposal 的“过去24h”与同文术语“默认当日00:00起”冲突。实现支持 `rolling24h` 和 `today`，默认后者；真实验收必须记录所用配置。
